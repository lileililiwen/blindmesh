## Blockers and remaining boundaries

The shared `Platform.*` packages are not adopted. The public platform feed answers 404, so the restore of a platform package fails visibly and the adoption stays blocked. The product does not replace the platform packages with a local copy. The probe, the blocked state and the retry command are in `docs/foundation/platform-adoption.md`.

`forge gate .` did not run: the Forge binary is not on PATH in this environment. The Gate manifest binds the native build, test and security checks and each of them passes when run directly.

The test harness of the foundation package had a defect that the participation package found: the runner of a native command waited for the end of the output of the child, and the reused MSBuild workers kept the inherited handle of the pipe open, so the suite hung for ten minutes. The runner now waits for the exit of the process and bounds the read of the output, so the plain `dotnet test` command reports the whole suite of 148 tests.

The release smoke on Firefox and WebKit did not run. Only the Chromium browser is installed in this environment.

`npm audit` reports high severity advisories in `braces`, `fast-glob` and `micromatch` through the dev-only `eslint-config-next` chain. The latest `braces` release is still affected, so there is no patched version to move to. The shipped production dependency set audits clean; the finding is recorded rather than hidden.

The grant eligibility of the seeded accounts belongs to the credit package. The identity package stores the provider email and does not decide the grant.

The matching scope of a project with the visibility `matched` is implemented. The rule of the scope is one method of the matching module, `ITaskMatchSeam.MatchesAsync`, and every read of a task asks it: a non-insider reads a task of the `public` scope when the project and the task are public, and a task of the `matched` scope only when the actor satisfies every hard condition of the task. The owner of a task reads the list of the accounts that fit it at `GET /v1/tasks/{id}/candidates`, and the order of that list is a named exploration rule that puts the accounts without an accepted contribution first. The answer carries no score, no weight, no percentage and no quality claim; the soft weights of the PRD stay unimplemented, because the PRD calls them hypotheses to calibrate. The push of a matched task is not implemented: the account that the list names is not told that it was listed, and a push belongs to the notification package.

The task publication package is implemented, so a published task with hard conditions exists. The eligibility route of a task answers with the conditions of that task through the seam `ITaskConditionReader`, whose implementation is now `PublishedTaskConditionReader`; a task that the actor may not see still answers 404.

The escrow primitives of the credit package — reserve, settle and refund — are internal methods of the credit service. There is no public transfer and no balance editor. The task publication package calls the reserve and the refund with the same database context and the same transaction as its own command, and the participation package calls the pending with the same rule. The evidence package now settles a seat with the same rule: a granted bonus moves from the reserved bucket of the publisher into the pending bucket of the contributor, the base and the bonus are paid out with the settle, and the unused bonus of the slot goes back to the publisher with the refund of an unstarted seat. The evidence package opens a dispute and holds the credits; the moderation package owns the case and the decision. The decision moves only the base of the seat. A bonus uses the pending primitive first, so it is refused with 409 when the cap of the task is exceeded, and an appeal compensates the paid amount with new journal rows. The signed sum of every transaction of a case is 0 and no account ever goes below zero.

The reputation of a contributor is derived from the events of the outbox, so the worker owns the projection. The evidence package writes the event of an accepted seat and the moderation package writes the event of a reversal, both inside the transaction of their own command. The worker registers the moderation module, because the findings module settles a seat through it, and it registers the matching module, because the project service asks the rule of the scope of the matching module. Without the latter the claim cycle of the outbox failed every cycle and the projection of the reputation never ran; the browser sweep of 2026-10-22 found it. The claim cycle counts only the messages it really applied, so an event without a handler does not keep the cycle busy.

The notifications of the workflow events are produced by the consumer of the outbox. The events that exist today cover the application of a seat, its acceptance, the submission of the evidence, the correction that the owner asks for, the acceptance of the seat, the update of a case and the outcome of an arbitration; the deadline and the refund have no producer yet and the module holds their category without faking a notification. The email goes out over a real SMTP connection with a stable Message-ID and a bounded retry of five delays; after the fifth failure the delivery is dead-lettered and an operator alert is written. The claim cycle of the outbox groups the handlers by event type, because the reputation and the notification modules both consume the same event.

The pilot operations own the recovery of the product. The restore rehearsal is real: it dumps the database with the client of PostgreSQL 17, restores it into an isolated database, checks the schema, the data, the objects and the ledger against the source, and drops the isolated database again. A failed check blocks the promotion and the previous image stays available. The paths of the clients are configuration (`Blindmesh:Operations:PgDumpPath` and its siblings), because a client that is older than the server refuses the dump. The gate reports the measured counts of the product and never a target as a measurement; P95 below 500ms and 99.5 percent availability stay targets until their observation window is documented.

The deferred scope of the PRD is not implemented. The pages say so instead of showing a fictional dashboard. Browser flows, responsive behavior and rendered accessibility exist for the runtime, for the identity, for the project workspaces, for the capability directory, for the wallet, for the task marketplace, for the seat of a contributor, for the evidence of a finished seat, for the moderation of the cases, for the reputation of a contributor, for the notifications, for the operations of the pilot and for the scoped matching only.
