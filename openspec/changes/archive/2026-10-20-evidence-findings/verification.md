## The decisions of this package

1. **The client of the object storage.** The product speaks the S3 API of a private bucket, and `docs/architecture.md` names "S3-compatible private object storage with AWS SDK for .NET". The package uses `AWSSDK.S3 4.0.104.5` from nuget.org, with the path style addressing and a separate client for the public address of the browser, so the signature covers the host the browser uses. A hand written SigV4 client was rejected, because a signature that is wrong in one detail makes every address unusable. The package adds `AWSSDK.S3` and `AWSSDK.Core` and nothing else.
2. **The check of a file is not an antivirus.** The environment of this package holds no antivirus engine, so the shipped check is honest and explicit: the declared name, the content type and the size are checked at the declaration, the bytes are compared with the declaration at the upload, the signature of the bytes is compared with the content type, and the bytes that carry the signature of an executable, of an archive, of an SVG or of an HTML file are refused, as the bytes that carry the test marker of the EICAR are refused. The state machine of a file is `quarantined -> scanned | rejected`, and a quarantined or a refused file is never readable. **This is not an antivirus engine and no malware scan is claimed.** A product that needs one needs a scanner service behind the same seam.
3. **The path of the bytes.** The browser never talks to the object storage directly, so the product never depends on a cross origin rule of the storage. The contributor declares the file, the browser sends the bytes to the API in a form, the API checks the bytes, writes them to the bucket outside the transaction and releases the row inside the transaction together with the record of the idempotency key. A direct upload of the browser to the bucket was rejected because of the cross origin risk, and a base64 body was rejected because it adds a third of the size to every file.
4. **The settlement of an accepted seat.** The acceptance locks the task, then the seat, then the slot and then the submission. It calls the credit service inside the same scoped database context and the same transaction as the write of the submission. A granted bonus above zero moves from the reserved bucket of the publisher into the pending bucket of the contributor with `BeginPendingAsync`; the base of the seat and the bonus are paid out with `SettleAsync`; the unused bonus of the slot goes back to the publisher with `RefundUnstartedAsync`. The credit module writes every entry of the escrow and the findings package never writes a ledger row.
5. **The timeouts of the review.** The worker owns a sweep that accepts the base of a seat whose evidence waits longer than 72 hours and that opens a dispute when a correction of 48 hours was not answered. The sweep reads the rows without a lock, locks the task first and then the seat and the submission, and it uses the injected clock, so the sweep and a command never produce two legal transitions. A correction may be asked only once, and a second request answers `409`.
6. **The boundary against the arbitration.** The dispute is opened here and resolved elsewhere. This package writes the state `disputed` on the submission, on the seat and on its slot, it writes the reason of the owner, and it moves no credit: the base of the seat stays pending and the bonus of the slot stays reserved until the arbitration of the moderation package decides. The package never resolves a dispute, never pays out a disputed seat and never confiscates the pay of a completed scope. The moderation package is the one that reads the disputed submission and writes the decision.
7. **The state of the seat follows the evidence.** The states `submitted`, `changes_requested`, `approved` and `disputed` of a seat and of its slot belong to this package, because the evidence causes them. The aggregate status of a task follows its seats under the lock of the task: a task that waits for a review is in review, a task whose seats are all settled is completed and a task without one is open again. The recompute lives in the participation service, which was made public for it, so the product has one implementation of the rule and not two.
8. **The writes across the modules.** The findings package writes the seat and its history through the public seam of the participation store, so the archived package keeps its ownership of its table. The findings package never writes the table of another module directly.
9. **Two endpoints and one table more than the design names.** The interface needs to read the reviews of a project and to read one finding, so the package adds `GET /v1/projects/{id}/reviews` and `GET /v1/findings/{id}`. The design asks to persist the expected version and the state history, so the package adds the table `submission_history` next to the five tables of the design.
10. **A file belongs to a submission.** The declaration of a file needs a submission, because the file belongs to the revision of the evidence and not to the seat alone. The rule of at most ten files per revision is then a property of the revision and not a counter of the seat.
11. **The limits of the evidence.** The limits of the design are the limits of the product: a summary of 1 to 5000 characters, a title of a finding of at most 140 characters, a reproduction of at most 10000 characters, an expected and an actual result of at most 5000 characters, ten files per revision, a text or a log of at most 2 MiB and a picture of at most 10 MiB. The package adds two limits that the design leaves open, because a body without a bound is a body the product cannot store: at most 50 findings and at most 50 tested areas per revision. A verification needs a result for every step of its task, an exploration needs the areas it covered, and a result without a finding needs the explanation of the contributor and a task that accepts a clean result.
12. **The columns of the history of a seat.** The migration widens `participation_history.from_status` and `participation_history.to_status` from `varchar(16)` to `varchar(32)`, because the new state `changes_requested` is longer than the old column. The change is a widening only; the rows of the earlier packages keep their values.

## The defects that were found and fixed

1. The assertion of the boundary test of the review expected no refund of the unused bonus after the acceptance of the worker. The acceptance of the worker does refund it, exactly once, because the bonus of the slot was never spent. The assertion was wrong and was corrected to one refund, and the journal of the test now proves that the publisher gets the unused bonus of the slot back.
2. The harness of the journeys served the old build of the web application after a new build, so the browser asked for a chunk that no longer existed and the page answered `500` without an error in the log of the product. The run of a journey group now restarts the web application after every build. This is a defect of the harness and not of the product.

## The checks that could not be run and the known limits

1. **An antivirus scan of a file.** No scanner runs in this environment, so no malware scan is claimed. The check that ships is the check of the declaration, the check of the signature and the refusal of the test marker of the EICAR. A file in the state `scanned` means that the declared bytes and the signature of the bytes agree, not that a virus scanner found nothing. A product that needs a scanner needs one behind the same seam.
2. **The release smoke in Firefox and WebKit.** The journeys ran in Chromium only, because the browsers of the other engines are not installed in this environment. The command for them is `npm --prefix apps/web run test:e2e -- --project=firefox --project=webkit --grep EVID`.
3. **The compose stack with the code of this package.** The stack of the host was not rebuilt for this package, because the containers belong to the host. The stack carries the image of the participation package. The FOUND journeys ran against the stack as it stands and passed; the journeys of this package ran against a local API and a local web application that carry the code of this package.
4. **The local Gate.** The command `forge gate .` of the design was not run, because the Forge command line is not available in this environment. Nothing about the Gate is claimed.
5. **The documentation captures.** No screenshot was captured, because the capture plan of `docs/assets/capture-plan.md` needs a running stack of the product with the data of the milestone. No capture is claimed.
6. **The default address of the object storage names the port of a MinIO.** `Blindmesh:ObjectStorage:Endpoint` in `appsettings.json` is `http://localhost:9000`, while the compose stack publishes its object storage on the port 59000. A host that starts without the environment of the compose stack therefore keeps the attachments unavailable and says so in the log. The value was not changed, because the file is shared with the earlier packages and the stack sets the value itself.
7. **The real object storage is proved by a manual exercise, not by an automated test.** The automated test of the pipeline uses a fake storage, so the suite stays fast and does not need a storage service. The proof of the real storage is the table of the step 12 and it is not part of the suite.
