# Design: Receive reliable in-app and email workflow notifications

## Context and implementation boundary

Notifications module and Worker handlers; notification_deliveries, notification_preferences and outbox records. GET /v1/notifications; POST /v1/notifications/{id}/read; GET/PATCH /v1/notification-preferences. Events: application received/accepted, deadlines, submission received, correction requested, acceptance, refund, dispute update and moderation outcome. Unique event+recipient+channel; status Pending/Sending/Sent/Failed, exponential retries 1m/5m/30m/2h/8h, then dead-letter and operator alert. In-app rows written once; SMTP submission is at-least-once with stable Message-ID, never promise exactly-once email. Recheck recipient permissions at send and read; email contains safe generic summary and authenticated relative deep link. No raw evidence or private titles in SMTP logs.

Exact backend boundaries: src/Blindmesh.Domain/Notifications, src/Blindmesh.Application/Notifications, src/Blindmesh.Infrastructure, src/Blindmesh.Api/Endpoints/Notifications. UI: apps/web App Router for /notifications, /settings/notifications. Tests: tests/Blindmesh.Tests/Notifications and tests/e2e/notification-delivery. Apply EF Core migrations only through Infrastructure/Persistence/Migrations; the API composition root wires services and the worker calls the same application methods. Alter only this package's modules and required composition/test hooks.

## User experience and interface

Routes: /notifications, /settings/notifications. Initial entry checks session/visibility, then loads the current state; anonymous private routes redirect to sign-in with an allowlisted return path or return a safe unavailable page. Skeletons announce loading without invented counts. Empty views explain the eligible next action. Inline validation associates messages with fields and focuses the first error. 401 offers sign-in; invisible resources return 404; visible forbidden actions explain the restriction. 409 prompts refresh while preserving draft input; 422 shows field/funds errors; 429 gives retry guidance; 503 offers bounded user retry. Disable duplicate pending submissions but rely on server idempotency. Confirm destructive consequences, show success after server commit and restore focus to the trigger. Never leak private fields in HTML metadata, client caches, notification previews or attachments.

NOTIF-UX: use the common shell and semantic tokens, light/dark pre-paint theme, 44px minimum targets, logical headings/landmarks, associated labels and aria-live status. At 360px use one column and labeled rows; at 768px collapse navigation; at 1440px use readable content width. No horizontal page overflow; maintain keyboard tab order, dialog focus containment/restoration, contrast and reduced-motion. Use shared primitives rather than bespoke auth/forms.

## Behavioral model, contracts and failures

- NOTIF-1 Delivery: The system SHALL deliver durable event-driven in-app notifications and retryable SMTP email with unique delivery identities, bounded retries and actionable operator failures.
- NOTIF-2 Preferences: The system SHALL expose accessible read/unread and preference controls while rechecking current authorization on notification previews and deep links.

HTTP native /v1 and same-origin browser /api/v1; snake_case JSON with GUID/UTC fields and integer long credits. Actor policy is rechecked on every command, list, detail, export and file lookup. Persist expected_version and state history. Mutating financial/publication/application/submission/review/moderation operations use scoped Idempotency-Key records in the same transaction. Lock task, participation/slot, sorted accounts, then ledger; retry serialization/deadlock at most three times. Never run network side effects inside the transaction. Save outbox effects atomically. Cross-module writes call the owning application service with the same scoped DbContext; only Credits writes ledger entries. Return 400/401/403/404/409/413/422/429/503 as defined in architecture, without provider/SQL details.

Migration introduces only package-owned tables/indexes/constraints and preserves prior rows. Verify fresh and upgraded PostgreSQL schemas. Failed commands leave no partial state; recovery uses a forward migration or compensating transaction, never rewrites settled data. Retryable reads show recovery controls; an ambiguous command timeout retries using its original key/payload.

## Verification oracle

Use the commands and seeded actors in verification.md. The acceptance boundary includes each success, rejection and boundary scenario in specs/notification-delivery/spec.md, the UI requirement and its mobile/keyboard/permission checks. Tests run against isolated real PostgreSQL; financial/concurrency checks assert journal sums and unique effects, not just HTTP responses. Browser tests exercise the committed state through generated clients. No test or browser claim is made during proposal authoring.

## Decision ledger

Chosen: product-local modular monolith and shared technical packages after foundation verification. Rejected: sibling runtime coupling, generic workflow engines, four task backends and ad hoc balance editing. Deferred: only the explicit non-goals/roadmap items. Dependencies must be verified and archived before this package is implemented. No material product decision is delegated to an implementer; an unavailable feed/runtime is recorded as a blocker with its exact retry command.
